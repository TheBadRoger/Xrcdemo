# 游戏版本适配指南

[返回 README](../README.md) · [插件功能](features.md) · [实现原理](architecture.md) · [安装方式](installation.md) · [**改动点总表（静态焊改/数据改动逐条）**](modifications-7.0.256.md)

本指南说明如何把现有练习插件迁移到新的 Arcaea iOS 版本。以当前 7.0.255 / 7.0.256 的实现为依据，涵盖定位、配置、代码调整、构建、部署和验收。

逐条改动清单（目的 / 位置 / 旧字节 → 新字节 / 换版本重定位锚点）见 [改动点总表](modifications-7.0.256.md)。

**适配不是只填一个 JSON。** JSON 描述注入位置；运行时还依赖函数接口、对象布局、指令语义、版本分支和功能处理器。地址相同或指纹匹配，都不能单独证明行为兼容。

## 1. 适配完成的标准

| 阶段 | 已完成什么 | 尚不能证明什么 |
| --- | --- | --- |
| 地址定位 | 找到候选函数、字段和补丁站点 | 调用约定和字段语义正确 |
| 接口核对 | 验证参数、返回值、单位、对象布局及调用路径 | 插件在设备上稳定运行 |
| 构建通过 | 对应版本的源码与测试可以编译执行 | 安装资格及真实游玩效果 |
| 注入检查通过 | 原指令、跳板、站点和加载命令符合预期 | 处理器运行时没有错误 |
| 安装启动通过 | 签名、包结构和启动链可用 | 所有练习功能均有效 |
| 功能验收通过 | 目标设备上逐项测试通过并保留证据 | 未测试系统、设备和模式也兼容 |

发布支持范围时应列出游戏版本、构建号、样本指纹、插件提交、设备系统和实际验证功能。不要把“面板能打开”写成“全部适配完成”。

## 2. 当前版本机制与文件清单

### 2.1 当前代码如何选版本

| 入口 | 当前行为 | 新版本需要处理 |
| --- | --- | --- |
| `inject.py → select_bundle_profile()` | 从主程序旁边的 `Info.plist` 读取 `CFBundleShortVersionString` | 保留实际版本识别，不靠文件名猜版本 |
| `inject.py → configure_profile()` | 只接受 7.0.255 / 7.0.256；255 使用内置基线，256 加载 JSON | 扩展白名单和 JSON 加载分支 |
| `Makefile → XRC_GAME_VERSION` | 默认 7.0.255；256 定义 `XRC_GAME_VERSION_7_0_256` | 添加显式编译分支，未知版本继续报错 |
| `XRCProfile.h` | 定义 255 基线，按宏引入 256 覆盖头 | 添加新版本覆盖头及选择分支 |
| `XRCKonzetsu.m` / `XRCHook.m` | 部分代码仅在 256 宏下编译 | 为新版本核对并启用对应实现，不能仅修改宏名字 |
| Actions 工作流 | 矩阵分别编译两个版本 | 添加新版本矩阵项与可辨识产物 |

目前不会自动扫描所有 `profiles/*.json` 并识别新版本。只新增一个文件而不改入口，注入器和 Makefile 仍会拒绝该版本。

独立运行 `--check` 时，如果主程序旁没有 `Info.plist`，当前代码会回退到 7.0.255。检查新版本应把主程序与正确的 Info.plist 放在同一 App 目录，不要误用回退配置。

## 3. 先建立样本与记录

### 3.1 准备材料

| 材料 | 要求 |
| --- | --- |
| 新版本 App | 已解密且满足插件兼容前提，包含对应资源与 Info.plist |
| 原始备份 | 保存完整未注入 App，分析与注入使用副本 |
| 旧版本样本 | 与已验证插件配置相对应，便于比较调用关系和布局 |
| 分析工具 | IDA 等能够读取 Mach-O、反汇编 ARM64 并查看交叉引用的工具 |
| 构建环境 | macOS 或 GitHub Actions；Windows 可用于定位和部署 |
| 设备 | 能导出插件日志、安装日志与崩溃报告的测试设备 |

同一个版本号可能有多个构建或不同修改来源。应记录 `CFBundleShortVersionString`、`CFBundleVersion` 和主程序 SHA-256；不要仅依赖 IPA 文件名。

PowerShell 记录示例：

```powershell
Get-FileHash -Algorithm SHA256 .\host\deployment\target-bin\main\Arc-mobile
python -c "import plistlib; p=plistlib.load(open('host/static/Payload/Arc-mobile.app/Info.plist','rb')); print(p.get('CFBundleShortVersionString'), p.get('CFBundleVersion'), p.get('CFBundleExecutable'))"
```

| 功能/符号 | 旧版本位置 | 新版本位置 | 原指令/布局 | 证据 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 场景每帧更新 | 待填写 | 待填写 | 参数、槽位、调用频率 | 调用者与设备日志 | 待核对 |
| 音频定位 | 待填写 | 待填写 | 时间单位、返回值 | 调用链与通道测试 | 待核对 |
| 流速基准字段 | 待填写 | 待填写 | 所属对象、类型、单位 | 构造写入与读取者 | 待核对 |
| 判定预筛选站点 | 待填写 | 待填写 | 指令、寄存器、继续执行位置 | 上下文与边界测试 | 待核对 |

每项都应有证据。未验证不能写成“沿用旧值”；可以记录“候选位置”，但不能用于发布配置。

## 4. 地址换算：先明确坐标系

| 名称 | 含义 | 用途 |
| --- | --- | --- |
| 静态 VA | 分析工具按首选 image base 显示的虚拟地址 | 标识指令和全局变量 |
| image offset | 静态 VA 减首选 image base | 运行时宏和 info blob |
| 运行时地址 | 实际加载的 image base 加 image offset | ASLR 后访问函数、对象或指令 |
| slice 内文件偏移 | 文件中的字节位置，相对于一个 Mach-O 架构切片 | 修改二进制 |
| fat slice 起点 | 通用二进制中某个架构切片的起始位置 | 换算为整个文件的偏移 |
| 对象字段偏移 | 某个字段相对于对象首地址的位置 | 读取运行时对象；不是代码地址 |

以实际段表为准，通用的文件换算为：

```text
image_offset = static_va - preferred_image_base
runtime_address = loaded_image_base + image_offset

slice_file_offset = segment.fileoff + (static_va - segment.vmaddr)
whole_file_offset = fat_slice_start + slice_file_offset
```

对应 VA 必须位于段的实际文件范围内；只有 `vmsize`、没有相应 `filesize` 的零初始化区域不能直接当文件字节改写。

**当前注入器的一些 BRK 路径直接使用 `slice_start + VA − 0x100000000`。** 这是现有样本的映射假设，不是所有 Mach-O 都成立。若新样本的段映射变化，应先调整注入器的地址换算，并同步检查清单生成和 `--check`，不能只在 JSON 里填一个“看起来正确”的 VA。

通用二进制还要检查实际安装架构与注入器处理的切片是否一致。函数名或地址在一个切片正确，不代表其他切片同样正确。

## 5. 定位函数与验证 ABI

### 5.1 推荐定位顺序

1. 找到游戏全局对象、GameScene、谱面管理对象和播放器。
2. 找到 GameScene 的每帧更新函数，核对实际调用频率。
3. 找到谱面时钟读取与更新时间链。
4. 找到音频位置查询、定位、音高/变速和 DSP 操作。
5. 找到判定核、判定提交与输入预筛选。
6. 找到回跳需要的音符重置、注册和渲染重建接口。
7. 核对流速、Konzetsu、内容和网络功能。

先完成基础播放、时钟与判定，再适配依赖这些基础的高级功能，便于缩小故障范围。

### 5.2 每个函数必须核对什么

| 检查 | 需要确认 |
| --- | --- |
| 所属对象 | `this` 指向哪种对象，是否仍是原类型 |
| 参数 | 整数、指针、浮点、栈参数的顺序、宽度与符号 |
| 返回值 | 布尔、整数、指针或结构体，是否通过隐藏返回缓冲区传递 |
| 行为 | 新函数是否仍完成旧处理器期待的动作 |
| 执行阶段 | 初始化、每帧、渲染、判定、结果页或下载回调 |
| 线程 | 游戏主线程、音频线程、后台下载线程或信号上下文 |
| 所有权 | 返回对象/缓冲区由谁创建、保留、释放 |

ARM64 中整数和指针参数通常经过 X 寄存器，浮点参数可能经过 SIMD 寄存器；不能把反编译器推测出的原型直接当事实。核对调用点及被调用函数的实际读写。结构体返回可能使用 X8 指向返回缓冲区，不能误当成普通 X0 返回值。

vtable 地址、槽号与槽内函数应分别记录。现有场景更新使用的槽位与初始化槽位不同；只找到“GameScene 相关函数”不够。场景初始化只执行一次，误用它会让变速、跳转和隐藏图标等每帧功能失效。

若新样本涉及 arm64e 指针认证，应沿用并验证项目的 PAC 处理路径，不能简单把带认证位的指针作为普通地址调用。

## 6. 核对对象字段与单位

字段定位应同时查看构造/初始化写入者和使用时的读取者，确认对象大小、类型和生命周期。

| 对象 | 必查字段 |
| --- | --- |
| GameScene | 谱面对象、渲染根节点、当前曲目标识与每帧状态 |
| note group / GameModel | LogicChart、谱面钟、音符数组、判定和计分对象 |
| 谱面钟 | 基础偏移、当前时间、分段时钟标志、曲首前导行为 |
| 音符 | 起止时间、判定标志、类型字段、子对象与数组范围 |
| 播放器 / 通道 | 音频句柄、通道位置、曲目长度和 DSP 状态 |
| UserPreferences | 普通/蓝牙偏移选择、偏移值、原生流速设置 |
| LogicChart | 已加载实际流速、谱面 AudioOffset、转换后的时间/距离数据 |

单位需要明确写在记录中：毫秒还是秒、流速本值还是十分之一整数、字节标志还是 32 位整数。不能因为字段同为 `int` 就认为语义相同。

### 6.1 当前实时流速实现的易漏项

| 接口或字段 | 语义 | 新版本核对方式 |
| --- | --- | --- |
| App 全局对象 + 112 | UserPreferences 指针 | 构造与 getter 的交叉引用 |
| UserPreferences + 12 | 流速乘十的 int32 | 原生 setter、持久化和显示消费点 |
| `XRC_OFF_FLOW_SETTER` | 写入并保存原生流速 | 参数 ABI、函数指纹和回读 |
| LogicChart + 240 | 加载时流速浮点值 B | 构造写入和距离计算 |
| Note + 48 / + 52 | 每帧相对距离 | 普通音符、Hold、Arc 各自更新函数 |
| Note + 56 / + 60 | 原生绝对距离 | 保持不变，不重新构造索引 |
| NoteGroup + 136 / + 144 | 空间索引容器首尾 | vector 和 map 的 ABI |
| map + 8；node + 32 | 树根；索引键 | 验证容器实现和键类型 |

距离处理器依赖浮点寄存器：普通音符与 Hold 使用 V0，Arc 使用 V1，在原生 `FCVTZS` 前处理两个 float 分量。候选查询处理器依赖 X19、S0、S9 及 NoteGroup + 24；必须逐站点核对寄存器语义，不能仅匹配指令字节。

当前实现不修改渲染根节点、节点 Z 缩放或原生显示窗口。旧 `adapt_window` 已退役；迁移时恢复其原指令，不能重新启用旧窗口写入。

## 7. 适配判定桩、BRK 与重放空间

### 7.1 判定跳板契约

当前判定跳板 v2 与 [xrc_abi.h](../src/core/xrc_abi.h)配套：

| 内容 | 当前契约 |
| --- | --- |
| handler 参数 | X0：note group；X1：note；X2：判定时刻；X3：由调用方 X6 透传 |
| slot | 24 字节：handler、原入口、预留字段 |
| info blob | 120 字节：magic、版本、六个地址偏移及预留区 |
| 未注册 handler | 跳板重放原入口指令并回到原生路径 |

若新判定链参数变化，需要改 handler 类型、跳板生成和调用处理，不是只换入口地址。若调整共享结构布局，应同步 Python 写入、C 读取、结构版本及检查器。

info blob 只传递已经定位的静态偏移，不会自动寻找未知新版本函数。运行时未找到 blob 时仍会使用编译期配置，错误的回退值同样危险。

### 7.2 每个 BRK 站点的定位记录

| 项目 | 记录内容 |
| --- | --- |
| 名称 | 与注入器、运行时表、功能组一致 |
| 站点 | 正确 VA、文件偏移及原始 4 字节 |
| 上下文 | 前后指令、寄存器值来源和活跃状态 |
| handler 行为 | 读取/修改哪些寄存器、对象或返回路径 |
| 重放区 | 可执行区域中的保留空间、原指令和返回分支 |
| 继续位置 | 正常重放后的 PC，或特殊 handler 的显式返回规则 |
| 功能归属 | 发布默认启用、可选、已退休或调试用途 |

复制旧 handler 前，逐项确认它所读的寄存器在新站点仍代表相同内容。前后指令相似并不保证寄存器分配相同。

### 7.3 重放与空间检查

- BRK 站点和 ARM64 指令按 4 字节对齐。
- 现有普通重放由“原始一条指令 + 返回分支”组成，至少需要 8 字节。
- 判定跳板、BRK 重放区、slot 与 info blob 不得互相覆盖。
- 可执行重放放在实际可执行映射；slot 需要可写，info blob 需要可读。
- 文件中的连续零字节并不自动证明可安全占用，还需检查段范围、引用和重定位信息。
- `B` 使用有符号 26 位立即数乘 4，范围约为正负 128 MiB；检查实际距离，不能硬套旧分支。
- `ADR`、`ADRP`、相对分支、literal load 等依赖 PC 的指令不能直接原样搬到新地址。

当前 `pc_relative_kind()` 会拒绝部分 PC 相对指令。若新站点不适合普通重放，应选择其他语义相同的站点，或实现经过验证的专用重定位/处理路径。不要为了注入成功删除检查。

当前某些特殊 handler 会显式设置 PC/LR 或跳过普通重放；应核对这种站点自己的返回契约，而不是统一假设每个站点都走同一种跳板。

### 7.4 信号上下文限制

BRK handler 在信号上下文运行。新增逻辑尽量只做受控的寄存器、整数和原子状态操作，不在里面分配内存、调用 Foundation、写日志、等待锁或读写文件。

当前综合时间表所需分配通过返回正常执行流中的桥接函数完成，不在信号处理器内直接构造复杂 C++ 容器。若新版本改变容器大小、结构体返回方式或释放责任，应一起调整桥接与所有权处理。

## 8. 按功能逐项适配

### 8.1 时钟、变速与跳转

| 项目 | 检查重点 |
| --- | --- |
| 谱面时钟 | 普通与分段分支、曲首负时间、base offset 的符号 |
| 每帧 retime | 修改倍率后保持连续，不重复累加偏移 |
| 音频位置 | getter/setter 的对象、单位、确认机制和返回码 |
| DSP | 创建、参数设置、挂接、释放及输出延迟 |
| seek 事务 | 主线程串行、场景/播放器变化、超时和冻结释放 |
| 校准 | 用户偏移、谱面 AudioOffset、DSP 延迟分别处理 |

跳转必须先确认音频落位，再提交谱面变化。新版本若原生更新改写时钟的时机变化，需要重新验证在原生 update 前后哪一阶段做校准，不能照搬旧调用顺序。

### 8.2 回跳重播、判定与自动演奏

核对各类音符的判定态、子对象、时间范围、注册接口和渲染重建路径。先测试 Tap，再测试 Hold、Arc、ArcTap，最后验证混合谱面。

判定调整不仅涉及最终评分函数，还可能依赖输入预筛选、音符过期和连续判定。漏掉前置窗口可能导致设置显示正确，但音符在到达新窗口前已经被过滤或判为丢失。

恢复显示不等于恢复可判定状态；强制重建也可能清空分数或造成重复计分。应检查显示、输入、判定与计分四条路径。

### 8.3 手动流速与倍率适配

| 项目 | 当前实现要求 |
| --- | --- |
| 原生设置 | setter 写入流速乘十整数，保存并回读；显示同步 |
| 输入范围 | 0.1–214748364.7，即 INT32_MAX / 10 |
| 距离系数 | S / B；开启自动适配后为 S / (B × r) |
| 距离站点 | 普通音符、Hold、Arc，在浮点转换为 int32 前处理 |
| 候选查询 | 系数小于一时扩大临时查询范围，并限定已有索引键边界 |
| 保持不变 | 节点 Z 缩放、渲染深度、原生显示窗口、绝对距离和索引键 |
| 退出覆盖 | 手动值零只取消覆盖，保留已保存的原生设置 |

`rate_flow` 包含 `flow_ui` 和六个 `native_flow_*` 站点，需同步 JSON、运行时头文件、处理器及 feature 注册。动态库必须包含 `practice-native-flow v1` 标记。原生流速显示与消费点的六处上限补丁也需迁移，不能只扩大面板输入范围。

验证 5.0 在 0.5 倍速自动补偿为内部 10.0，显示仍是 5.0；手动改为 10.0 时显示也必须改为 10.0。分别检查 Tap、Hold、Arc、ArcTap、特殊 timing group、跳转和中途开关，并核对深度及显示窗口未被写入。

### 8.4 Konzetsu

| 项目 | 必查内容 |
| --- | --- |
| 编译条件 | 当前只实现 7.0.256 分支，新版本需要明确接入 |
| 六个接口 | 谱面快照、挑战 ID、活跃状态、计分/血条类型、血条 UI、综合时间表 |
| 调用范围 | `s_effect_caller()`、`s_gauge_caller()` 及其他 caller 范围 |
| 管理器布局 | 全局对象到管理器的字段、当前挑战字段 |
| 谱面数据 | ParsedSong 数组、音符时间、时间表参数与类型 |
| 参数寄存器 | 血条初始化和效果选择的传递位置 |
| 返回 ABI | 时间表结构大小、隐藏返回缓冲区、对象所有权 |
| 范围控制 | 只影响练习转换/渲染/血条，不覆盖原生真实通关状态 |

当前 `XRCHook.m` 中六个 Konzetsu 站点仍有直接写出的 256 地址；`XRCKonzetsu.m` 中还有函数起止范围。新版本的 JSON 站点变化后，这些位置也必须同步。

界面第四个选项“点血条”映射到对应原生逻辑，不应按界面序号机械等同内部 ID。普通歌曲综合模式的模板与时长映射也需检查新版本原生效果语义。

### 8.5 内容与网络

网络检查 ObjC 类、selector、方法原型及回调顺序；名字没变也需要启动测试。发布版本不要无意恢复已排除的全局诊断钩子。

内容检查实际 cb 路径、目录链接、元数据格式、覆盖层选择和初始化时机。若新版本改变这些规则，不能继续拿旧 `meta.cb` 证明资源已就绪。App 包内资源和数据容器内热更新分别部署。

## 9. 编写新版本 JSON 与覆盖头

### 9.1 JSON 字段说明

| 字段 | 含义 | 注意 |
| --- | --- | --- |
| `game_version` | 配置对应版本 | 与 Info.plist 和编译版本一致 |
| `source_sha256` | 定位时使用的主程序指纹 | 当前加载配置不会仅凭该字段自动拒绝所有不同哈希；需另做样本核对 |
| `constants` | 跳板的 VA/FILE、slot/info 与运行时锚点 | 明确每个键的坐标系 |
| `stub_entry_expect` | 判定入口被替换指令的原始字节 | 当前入口方案使用 12 字节，需与生成器一致 |
| `brk_hooks` | 名称、站点 VA、重放 VA、原字节 | 不是对象字段配置表 |
| `restore_sites` | 需要恢复的旧站点和原字节 | 同样按新样本定位，不能沿用旧恢复地址 |

当前配置中的十六进制地址使用字符串，Python 用 `int(value, 0)` 读取；指令字节使用文件中的小端顺序，而不是反汇编器显示的数值顺序。

例如现有 **7.0.256** 的一项如下，仅用于理解格式，不能作为新版本的定位结果：

```json
[
  "native_flow_note",
  "0x100865b50",
  "0x10146c1c0",
  "00b8a10e"
]
```

对应运行时宏存的是 image offset，而不是绝对 VA：

```c
#undef XRC_NATIVE_FLOW_NOTE_SITE_OFF
#define XRC_NATIVE_FLOW_NOTE_SITE_OFF (0x865B50ULL)
#undef XRC_NATIVE_FLOW_NOTE_REPLAY_OFF
#define XRC_NATIVE_FLOW_NOTE_REPLAY_OFF (0x146C1C0ULL)
```

复制旧 JSON 作为模板后，应逐项标记待验证。不要因为只发现几项地址变化，就默认其余项均正确。

### 9.2 覆盖头继承的陷阱

`XRCProfile_7_0_256.h` 采用 `#undef` / `#define` 覆盖基线。遗漏的宏会继承 255 值，编译通常仍能通过。因此新版本至少要建立一张“已重定位 / 已证实不变 / 未验证”的完整宏清单。

建议把新增的硬编码地址、字段和 caller 范围集中成版本配置。确认语义一致的公共常量可共享；未验证的数据不能借继承机制隐式带入新版本。

## 10. 接入新版本入口与配对检查

以“新版本 N”表示目标，不假定具体版本号：

1. 新建 `profiles/ios_N.json` 和对应运行时覆盖头。
2. 修改 `configure_profile()`，显式接受 N 并加载其配置；每次切换前恢复基线，避免前一个配置泄漏。
3. 修改 `features_selected()` 中按版本过滤的功能，例如 Konzetsu。
4. 修改 `Makefile`，为 N 定义明确的编译宏，保留未知版本报错。
5. 修改 `XRCProfile.h` 的头文件选择和 `XRC_GAME_PROFILE_MARKER`。
6. 接入各功能的编译条件、站点表和 caller 范围。
7. 修改注入前动态库版本检查，要求 N 的配套标记。
8. 添加工作流矩阵项，产物名称带游戏版本。
9. 添加 N 的配置、切换与错误拒绝测试。

同一接口 ABI 保持一致时可保留功能标记；若 handler 或重放契约变化，应升级标记并要求新动态库。配对检查要覆盖将要写入的站点，也要考虑主程序已经存在的新增站点，避免旧动态库加载后命中未知 BRK。

`XRCVersion.h` 的显示版本与 CI 构建戳不负责游戏兼容性选择，不能通过改显示版本替代上述步骤。

### 遗留表也要处理

`inject.py` 的 `FLOW_RUNTIME_PATCHES` 目前按两个版本建立表，用于历史流速消费点的应用/恢复与检查。当前原生流速功能使用这张表解除显示与消费点的旧上限。新增 N 时需明确兼容的恢复计划或改为可选机制，不能留下未处理的字典访问。

同样检查旧 `RESTORE_SITES`、已退休功能、恢复原指令的运行时表和诊断指纹。当前没有启用某功能，并不意味着它完全不会被部署或检查代码读取。

## 11. 验证配置与构建

### 11.1 静态与测试检查

```sh
python -m json.tool profiles/ios_N.json
python -m unittest discover -s src/tests -v
git diff --check
```

这里 `N` 是占位符，执行前替换为真实版本。JSON 语法通过只说明格式正确。

| 测试类型 | 新版本应覆盖 |
| --- | --- |
| 配置切换 | 旧版 → 新版 → 旧版后不残留地址 |
| 版本拒绝 | 未适配版本明确报错；不要把新支持版本留作“未知版本”测试样本 |
| 站点 | 名称一致、原字节长度正确、有效重放区域不发生未规划重叠 |
| 补丁行为 | 注入后的站点、重放内容、返回分支及必要恢复正确 |
| 旧产物拒绝 | 配对失败发生在复制/修改 App 前 |
| 数学 | 新单位或布局不破坏偏移、流速和跳转边界 |
| 能力 | 功能缺失时禁用对应控件，不把保存配置当成运行成功 |

现有测试中有写死的旧版本列表和地址预期。增加新版本用例，同时保留旧版本回归；不要把全部测试改成只检查新版本。

### 11.2 构建

```sh
make clean
make XRC_DEBUG=0 XRC_GAME_VERSION=N
```

或在 Actions 运行添加了 N 的工作流。确认完整 C 测试与插件编译通过，检查动态库架构、安装名、依赖和版本标记。

Windows 本地显示 C 测试跳过时，不是完整验证。以 macOS 的完整测试和编译结果为依据。构建后记录提交哈希及对应版本产物，不混用不同运行记录中的库。

## 12. 注入、检查、打包和签名

在独立 App 副本中放入新版本 Info.plist 和主程序，准备匹配动态库后运行：

```sh
python inject.py --stub --brk --profile release
python inject.py --check host/deployment/target-bin/main/Arc-mobile
```

| 结果 | 处理 |
| --- | --- |
| 原字节断言失败 | 比较样本、地址坐标和已有修改，不强行写入 |
| 重放空间非零 | 核对是否已有有效重放或被其他内容占用 |
| 功能标记不匹配 | 核对动态库来源和新版本配对规则 |
| 判定桩 v2 / dylib 加载在位 | 继续检查全部选定站点，不只看最后一行 |
| 恢复或未预期状态异常 | 检查清单与原始备份，确认没有恢复/修改错位置 |

从副本打包，保持用户资源，去除分析数据库、日志、旧签名及不需要的扩展。cb 热更新按实际容器布局单独部署，不重复装入 IPA。随后重新签名并安装，完整步骤见 [安装方式](installation.md)。

本地 `host/deployment` 的专用打包和签名脚本可能固定了样本版本、预期哈希或产物名称。新版本需要同步这些本地参数；不能把上一个版本的已准备主程序副本直接装进新包。

## 13. 真机验收顺序

| 顺序 | 场景 | 通过条件 |
| --- | --- | --- |
| 1 | 安装、冷启动、重启 | 无安装错误、启动超时或缺少动态库 |
| 2 | 面板与日志 | 游戏 profile、构建戳与目标版本一致，能力探针合理 |
| 3 | 1x 普通游玩 | 谱面、音乐、判定和计分均正常 |
| 4 | 多倍率 | 低倍率 / 1x / 高倍率音画稳定；音乐变速开关行为正确 |
| 5 | 进度跳转 | 前进、回退、曲首、快速连续拖动、取消均正确 |
| 6 | 循环与重播 | 短/长循环、回跳重播开关、已判音符恢复正确 |
| 7 | 暂停、Retry、换歌 | 不操作旧对象、不擅自恢复音频、无冻结残留 |
| 8 | 判定 | 四档边界，Tap / Hold / Arc / ArcTap，锁定开关分别通过 |
| 9 | 实时流速 | 普通值、低值、高值、恢复原生、倍率叠加和中途设置 |
| 10 | Konzetsu | 五项切换、重新开局、任意普通歌曲、两种血条和原生挑战 |
| 11 | 图标 | 游玩隐藏、停止更新后恢复、开关状态保存 |
| 12 | 内容和网络 | 文件共享、cb 初始化、更新状态、私服请求按需验证 |

先使用简单、短、资源完整的谱面隔离问题，再测试复杂谱面和功能组合。达到 INT_MAX 的输入应先验证保存与溢出边界，不把“能输入”当成“极端值视觉可用”。

运行闪退保留 `.ips` 和 `Documents/xrcdemo.log`；安装失败保存 `installd` 日志。报告同时写明操作步骤、倍率、开关、曲目、插件构建及游戏样本，便于重现。

常用日志关注 `[probe]`、`[seek]`、`[rate]`、`[adapt]`、`[flow-live]`、`[konzetsu]`；具体以当前构建实际输出为准。

## 14. 常见“看似适配、实际无效”情况

| 表现 | 常见遗漏 |
| --- | --- |
| JSON 新增后仍报 unsupported | 版本白名单或加载分支未接入 |
| 编译通过但启动崩溃 | 基线宏误继承、字段/ABI 错误、遗漏 caller 范围 |
| 面板缺少新功能 | 能力探针仍读旧入口，编译条件或功能组未更新 |
| 开关能保存但没有效果 | 寄存器语义错误、旧动态库、新站点不完整 |
| 第一次跳转就偏移 | 时钟字段、单位、DSP 延迟或收敛顺序变化 |
| 重播能显示但不能判定 | 只恢复渲染，未恢复判定态或注册关系 |
| 中途流速不起效 | 读菜单值而非加载基准，原生 setter 未写入、距离站点缺失或候选检索失败 |
| 挑战只对部分歌曲有效 | 转换范围、时间表、实际加载快照或原生效果语义遗漏 |
| 内容下载后仍重复下载 | 元数据格式、容器路径或版本关系变化 |
| `--check` 看似正常但版本错误 | 样本旁缺 Info.plist，回退到旧版配置 |
